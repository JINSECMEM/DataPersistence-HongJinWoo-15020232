# 데이터 영속성 PoC 설계 문서

## 1. 개요

반도체 시료 생산 관리 시스템의 데이터 영속성(Data Persistence) 처리에 대한 PoC(Proof of Concept)이다.  
구체적인 DB 스펙은 확정 전이므로, 최소한의 구조로 핵심 동작을 검증하는 것이 목표이다.

---

## 2. 기본 데이터 단위

**시료 (Sample)**

| 필드 | 타입 | 설명 |
|------|------|------|
| `id` | string | 시료 고유 식별자 |
| `name` | string | 시료명 |
| `status` | enum | 생산 상태 (예: `created`, `in_process`, `completed`, `defect`) |
| `created_at` | string | 생성 일시 (ISO 8601) |
| `updated_at` | string | 최종 수정 일시 (ISO 8601) |

> 필드 구성은 PoC 범위에서 최소화하며, 이후 스펙 확정 시 확장한다.

---

## 3. 파일 포맷

- 확장자: `.db`
- 인코딩: UTF-8 텍스트
- 구조: CSV 기반 또는 Key=Value 라인 포맷 (파싱 구현 단순화 목적)

### 예시 (CSV 방식)

```
id,name,status,created_at,updated_at
S001,SampleA,completed,2026-05-08T09:00:00,2026-05-08T11:30:00
S002,SampleB,in_process,2026-05-08T10:00:00,2026-05-08T12:00:00
S003,SampleC,defect,2026-05-08T08:00:00,2026-05-08T13:00:00
```

## 4. 동기화 전략 — Lazy Sync

프로그램 실행 중 DB는 메모리(In-Memory) 상태로만 운영되며,  
파일과의 동기화는 프로그램 생명주기의 양 끝에서만 수행한다.

```
[프로그램 시작]
      │
      ▼
 .db 파일 읽기 → 메모리 로드
      │
      ▼
 [런타임: 메모리 기반 CRUD]
      │
      ▼
 [프로그램 종료]
      │
      ▼
 메모리 최종 상태 → .db 파일 쓰기
```

### 트리거

| 이벤트 | 동작 |
|--------|------|
| 프로그램 시작 | `.db` 파일 → 메모리 로드 (파일 없으면 빈 상태로 초기화) |
| 프로그램 종료 | 메모리 최종 상태 → `.db` 파일 덮어쓰기 |

## 5. 구성 요소

```
┌─────────────────────────────────┐
│           Main (진입점)          │
│  - 시작 시 DBManager::Load() 호출 │
│  - 종료 시 DBManager::Save() 호출 │
└────────────┬────────────────────┘
             │
┌────────────▼────────────────────┐
│           DBManager             │
│  - Load(filepath) : DB → Memory │
│  - Save(filepath) : Memory → DB │
│  - Add / Get / Update / Delete  │
└────────────┬────────────────────┘
             │
┌────────────▼────────────────────┐
│        In-Memory Store          │
│  std::vector<Sample> 또는        │
│  std::unordered_map<id, Sample> │
└─────────────────────────────────┘
```

---

## 6. PoC 검증 항목

| # | 검증 항목 | 기준 |
|---|-----------|------|
| 1 | 시작 시 `.db` 파일 정상 파싱 및 메모리 로드 | 파일 내 레코드 수 == 메모리 레코드 수 |
| 2 | 파일 없을 때 빈 상태로 정상 초기화 | 예외 없이 실행 |
| 3 | 런타임 중 시료 추가/수정/삭제 | 메모리 상태 즉시 반영 |
| 4 | 종료 시 메모리 → `.db` 파일 정상 저장 | 재시작 후 동일 데이터 로드 확인 |
| 5 | 비정상 종료 시 데이터 손실 허용 여부 확인 | Lazy Sync 한계 인지 |

---

## 7. 제약 및 향후 고려사항

- **동시성**: 단일 프로세스 단일 스레드 가정. 멀티스레드 환경은 PoC 범위 외.
- **원자성**: 비정상 종료(crash) 시 마지막 Save 이전 변경 사항은 유실됨. PoC에서 허용.
- **스펙 변경 대응**: DBManager 인터페이스를 추상화하여 이후 SQLite 등 실제 DB 교체 시 내부만 교체 가능하도록 설계.
- **파일 포맷**: CSV → JSON → Binary 등으로 전환 가능성 열어 둠.
